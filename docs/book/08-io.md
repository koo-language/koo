# Chapter 8: Input and Output

Input and output facilities are not part of the Koo language itself, so we have not emphasized them in our presentation thus far. Nonetheless, programs interact with their environment in much more complicated ways than those we have shown before. In this chapter we will describe the standard packages `std/io` and `std/os`, which read and write text and files and deal with the program's surroundings, the way any value is turned into text and, as JSON, back again, and `std/time`, which tells the time.

## 8.1 Standard Input and Output

As we said in Chapter 1, the library implements a simple model of text input and output. A text stream consists of a sequence of lines; each line ends with a newline character.

The simplest input mechanism is to read one line at a time from the *standard input*, normally the keyboard, with `io.read_line`:

    io.read_line() -> string?

`read_line` returns the next line of input each time it is called, without its newline, or `none` when it encounters end of file. In many environments, a file may be substituted for the keyboard by using the `<` convention for input redirection: if a program `prog` uses `read_line`, then the command line

    prog < infile

causes `prog` to read lines from `infile` instead. The switching of the input is done in such a way that `prog` itself is oblivious to the change. Input switching is also invisible if the input comes from another program via a pipe mechanism: the command line

    otherprog | prog

runs the two programs `otherprog` and `prog`, and pipes the standard output of `otherprog` into the standard input for `prog`.

`io.read_lines()` reads all the lines that remain, and returns them as a list.

The function `print(value)` writes a value and a newline on the *standard output*, which is by default the screen, and `io.write(text)` writes a string and nothing else. Output can be directed to a file with `> outfile`, or into another program with a pipe. Output is collected in the program and written in large pieces, which is much faster than writing each line as it is produced; all of it has been written by the time the program ends, whether it ends by returning from `main`, by `os.exit`, or by a panic.

Many programs read only one input stream and write only one output stream; for such programs, input and output with `read_line`, `print` and `write` may be entirely adequate, and are certainly enough to get started. For example, consider the program `lower`, which converts its input to lower case:

```koo
import std/io

// Convert the input to lower case.
fn main() {
    while line := io.read_line() {
        print(line.to_lower())
    }
}
```

```input
Now Is The Time
FOR ALL GOOD PEOPLE
```

```text
now is the time
for all good people
```

`print` needs no import, since nearly every program uses it. Everything else in this chapter comes from a package and is called by the package's name: `io.read_line`, `os.args`.

## 8.2 Formatted Output

Koo has no `printf`. Formatted output is written with what we have used all along: a string, with the values to be shown written inside it in braces. Between the braces is an expression, and it may be any expression at all, a call or a formula as well as a name.

After the expression there may be a colon and a *format*, which says how the value is to be laid out. A format is, in this order, and each part optional:

- An alignment: `<` to put the value at the left of its field, `>` to put it at the right, `^` to center it. Without one, a number goes to the right and anything else to the left.
- A `0`, which pads a number on the left with zeros in place of blanks, after its sign.
- A number, the minimum width of the field. A value that is wider than its field is printed in full: a width never cuts anything off.
- A period and a number, for a `float` the number of digits after the decimal point.

The following table shows the effect of a variety of formats in printing the integer 42, the float 3.14159 and the string `koo`. We have put brackets around each field so you can see its extent.

```koo
fn main() {
    n := 42
    x := 3.14159
    s := "koo"
    print("[{n}] [{n:6}] [{n:<6}] [{n:^6}] [{n:06}] [{-n:06}]")
    print("[{x}] [{x:.2}] [{x:8.2}] [{x:<8.2}] [{x:08.2}] [{x:.0}]")
    print("[{s}] [{s:6}] [{s:>6}] [{s:^7}] [{s:2}]")
}
```

```text
[42] [    42] [42    ] [  42  ] [000042] [-00042]
[3.14159] [3.14] [    3.14] [3.14    ] [00003.14] [3]
[koo] [koo   ] [   koo] [  koo  ] [koo]
```

With these few pieces most tabular output can be produced. As an example, here is a program that prints a small table of squares and square roots:

```koo
fn main() {
    print("{"n":>3} {"square":>7} {"root":>8}")
    for n in [1, 2, 10, 144] {
        print("{n:3} {n * n:7} {float.from(n).sqrt():8.4}")
    }
}
```

```text
  n  square     root
  1       1   1.0000
  2       4   1.4142
 10     100   3.1623
144   20736  12.0000
```

A string constant inside the braces, like `"n"` in the first line, is an expression like any other, and may be given a width.

## 8.3 The Text Form of a Value

Every value in Koo has a *text form*, which is what `print` writes, what `{...}` puts in a string, and what the method `to_string()` returns.

```koo
type Point = { x: int, y: int }
enum Shape { Dot, Circle { radius: float } }

fn main() {
    print(42)
    print(2.0)
    print(true)
    print("plain")
    print(["quoted", "inside"])
    print((1, "pair"))
    print(["key": [1, 2]])
    print(Point { x: 1, y: 2 })
    print(Shape.Circle { radius: 0.5 })
    present: int? = 7
    absent: int? = none
    print("{present} {absent}")
    print(Point { x: 1, y: 2 }.to_string().len)
}
```

```text
42
2.0
true
plain
["quoted", "inside"]
(1, "pair")
["key": [1, 2]]
Point { x: 1, y: 2 }
Circle { radius: 0.5 }
7 none
20
```

A `float` always shows a decimal point or an exponent, so that it cannot be mistaken for an integer. A string by itself is written as its characters; a string *inside* something else, a list or a structure, is written in quotes, with escape sequences where they are needed, so that the form is unambiguous. A structure shows its type and fields, unless it has a `to_string` method of its own (Section 6.3), in which case that is used everywhere.

The text form is meant for people: for messages, for logs, and for the programmer who wants to see what a value is. For data that another program will read, use JSON, in Section 8.7.

## 8.4 Command-line Arguments

In environments that support Koo, there is a way to pass command-line arguments or parameters to a program when it begins executing. The function `os.args()` returns them as a list of strings.

The simplest illustration is the program `echo`, which echoes its command-line arguments on a single line, separated by blanks. That is, the command

    echo hello, world

prints the output

    hello, world

```koo
import std/os

// Echo the command-line arguments.
fn main() {
    print(os.args().join(" "))
}
```

```args
hello,
world
```

```text
hello, world
```

By convention in C the first argument is the name by which the program was invoked. In Koo the list has only the arguments proper, so for a program run with no arguments it is empty. When a program is run by `koo run`, its arguments follow a `--` that separates them from those of the compiler:

    koo run echo.koo -- hello, world

As a second example, let us make some enhancements to the pattern-finding program from Section 4.1. If you recall, we wired the search pattern deep into the program, an obviously unsatisfactory arrangement. Following the lead of the UNIX program `grep`, let us change the program so the pattern to be matched is specified by the first argument on the command line. Let us also allow for two optional arguments. One says "print all lines *except* those that match the pattern"; the second says "precede each printed line by its line number."

A common convention for C programs on UNIX systems is that an argument that begins with a minus sign introduces an optional flag or parameter. If we choose `-x` (for "except") to signal the inversion, and `-n` ("number") to request line numbering, then the command

    find -x -n pattern

will print each line that doesn't match the pattern, preceded by its line number.

```koo
import std/io
import std/os

// Print the lines that match the pattern given by the first argument.
fn main() {
    var except := false
    var number := false
    var pattern: string? = none
    for arg in os.args() {
        match arg {
            "-x" => except = true
            "-n" => number = true
            _ if arg.starts_with("-") => {
                io.eprint("find: illegal option {arg}")
                os.exit(2)
            }
            _ => pattern = arg
        }
    }
    wanted := pattern else {
        io.eprint("usage: find -x -n pattern")
        os.exit(2)
        return
    }

    var line_number := 0
    while line := io.read_line() {
        line_number += 1
        if line.contains(wanted) != except {
            if number {
                io.write("{line_number}:")
            }
            print(line)
        }
    }
}
```

```args
-x
-n
ould
```

```input
Ah Love! could you and I with Fate conspire
To grasp this sorry Scheme of Things entire,
Would not we shatter it to bits -- and then
Re-mould it nearer to the Heart's Desire!
```

```text
2:To grasp this sorry Scheme of Things entire,
```

`io.eprint` writes a line on the *standard error* output, which is where messages belong: it goes to the screen even when the standard output has been redirected to a file or a pipe. `os.exit(status)` ends the program at once with the given status. By convention, a status of 0 signals that all is well; non-zero values usually signal abnormal situations. (The `return` after it is there for the compiler, which wants every path through the `else` to leave.)

## 8.5 The Environment

Besides its arguments, a program is given an *environment* by the system that runs it: a set of named strings, such as the name of the user's home directory. `os.env(name)` returns the value of an environment variable, as an optional, since the variable may not be set.

```koo
import std/os

fn main() {
    port := int.parse(os.env("KOO_BOOK_PORT") else "8080") else 8080
    print("listening on port {port}")
    print(os.env("KOO_BOOK_NO_SUCH_VARIABLE"))
}
```

```text
listening on port 8080
none
```

The first line of `main` is the idiom for a setting with a default: the variable's value if it is set, or else the text `"8080"`; and the number that is, or 8080 if it is not a number.

That is well enough for one setting. A service has a dozen, and it is in the environment that a service is told everything that differs between one place it runs and another: where its database is, which port to listen on, how long to wait. So the settings are declared together, as a structure, and the compiler writes a function `from_env` that reads the structure from the environment, each field from the variable of its name in capitals:

```koo
type Settings = {
    store_url: string,
    listen_port: int = 8080,
    request_timeout: Duration = 5s,
    verbose: bool = false,
    region: string?,
}

fn main() {
    match Settings.from_env() {
        settings => print(settings)
        ! e => print("cannot start: {e}")
    }
}
```

```env
STORE_URL=postgres://db.internal/shop
REQUEST_TIMEOUT=750ms
VERBOSE=yes
```

```text
Settings { store_url: "postgres://db.internal/shop", listen_port: 8080, request_timeout: 750ms, verbose: true, region: none }
```

The rules are those of a structure read from JSON (Section 8.7). A field with a default keeps it when its variable is not set, as `listen_port` did; an optional field is then `none`; and any other field must be set. A field is an `int`, a `float`, a `bool`, a `string`, a `Duration`, a `Time`, a `Date`, a `Decimal` or a `Zone` (Sections 2.5 and 8.8), or an optional of one; each is written as its type's `parse` reads it, a `Duration` as `250ms`, a `Date` as `2026-01-31` and a `Zone` by its name, and a `bool` is `true` or `false`, with `1`, `0`, `yes`, `no`, `on` and `off` understood too.

When something is wrong, `from_env` fails with an `EnvError`, which has the `name` of the variable and a `message`. A program whose settings are wrong should say so and stop, at once, when it starts, and not at three in the morning when the setting is first used. Here is the same program started with nothing set:

```koo
type Settings = {
    store_url: string,
    api_key: string,
    listen_port: int = 8080,
}

fn main() {
    match Settings.from_env() {
        settings => print(settings)
        ! e => print("cannot start: {e}")
    }
}
```

```text
cannot start: the environment variables `STORE_URL`, `API_KEY` are not set
```

Every variable that is missing is named, not only the first, so that it takes one attempt to find out what a program needs and not as many as it has settings.

A program is told one more thing by the system it runs on, and that not when it starts: that it is to stop. The signal for it, which a terminal sends for Ctrl-C and a system that runs services sends before it takes a program away, ends a program at once, in the middle of whatever it is doing. A server deals with it by itself (Section 10.7). A program that is no server but should finish what it is at, one that takes jobs from a queue, asks:

    while not os.stopping() {
        job := queue.pop("jobs", wait: 2s)? else { continue }
        work(job)
    }

`os.stopping()` says whether the program has been told to stop. From the first time a program asks, the signal ends nothing: it is only what `os.stopping()` then says, and the program is to end by itself, soon. A wait that is going on when the signal comes is not cut short, so the waits of such a loop are best short ones. The same holds for a program with a server in it (Chapter 10): one that has asked, from `main` or from a handler, is not ended by the signal after `serve` has returned either, and `os.stopping()` then says `true`, since being told to stop is why `serve` returned.

## 8.6 File Access

The examples so far have all read the standard input and written the standard output, which are automatically defined for a program by the local operating system.

The next step is to write a program that accesses a file that is *not* already connected to the program. One program that illustrates the need for such operations is `cat`, which concatenates a set of named files onto the standard output. `cat` is used for printing files on the screen, and as a general-purpose input collector for programs that do not have the capability of accessing files by name. For example, the command

    cat x.koo y.koo

prints the contents of the files `x.koo` and `y.koo` (and nothing else) on the standard output.

The package `std/io` has two functions for files, each of which deals with a whole file at once:

    io.read_file(path: string) -> string ! IoError
    io.write_file(path: string, text: string) ! IoError

`read_file` returns the contents of the file as a string. `write_file` makes the file if it does not exist, and replaces what it contained if it does. Either can fail, in the many ways that the world can frustrate a program that wants a file: the file is not there, the program is not permitted to read it, the disk is full. All of them are the one error type `IoError`, which has a field `message` that tells in words what went wrong.

```koo
import std/io
import std/os

// Concatenate files.
fn main() {
    var failed := false
    for path in os.args() {
        match io.read_file(path) {
            text => io.write(text)
            ! e => {
                io.eprint("cat: {e.message}")
                failed = true
            }
        }
    }
    if failed {
        os.exit(1)
    }
}
```

Suppose there are two files beside the program,

```file one.txt
The first file
has two lines.
```

```file two.txt
The second has one.
```

and that it is run with the arguments

```args
one.txt
missing.txt
two.txt
```

Then it prints

```text
The first file
has two lines.
The second has one.
```

on its standard output, and on its standard error

```stderr
cat: cannot read missing.txt: No such file or directory
```

The program carries on after a file that it cannot read, as `cat` should, and remembers the failure so as to end with a status that says so. A program that would rather stop at the first trouble needs none of this: it declares `main` as `fn main() ! IoError`, writes `io.read_file(path)?`, and the message and the status take care of themselves, as Section 7.6 described.

A string holds text, and `read_file` reads text. A file whose bytes are not valid UTF-8 cannot be read into a string, since no string may hold such bytes, and `read_file` fails on it with an `IoError` that says so.

Here is a program that keeps a count of how many times it has been run, in a file, as a small example of reading and writing together:

```koo
import std/io

fn main() ! IoError {
    path := "runs.txt"
    runs := int.parse((io.read_file(path) else "0").trim()) else 0
    io.write_file(path, "{runs + 1}\n")?
    print("this is run number {runs + 1}")
    print(io.read_file(path)?.trim())
}
```

```text
this is run number 1
1
```

The first read fails the first time, when there is no file, and the `else` supplies a count of zero: an error is handled where the program knows what to do about it, and passed on, with `?`, where it does not.

## 8.7 JSON

Programs talk to other programs far more often than to people, and the common tongue of such talk at present is JSON. In most languages, reading and writing JSON is the business of a library, and of some ceremony in the declaration of each type that is to be read or written. In Koo it is built in, and there is no ceremony.

Every structure and enumeration that is made of what JSON can express has a method `to_json()` that returns its value as JSON text, and a function `from_json(text)` that reads a value back. There is nothing to import and nothing to declare. A structure or an enumeration with type parameters, a `Page<T>` or an `Outcome<T, E>`, has them for every `T` and `E` that do.

```koo
enum Status { Open, Shipped }

type Item = { sku: string, qty: int = 1, note: string? }
type Order = { id: int, items: [Item], status: Status }

fn main() {
    order := Order {
        id: 7,
        items: [Item { sku: "a-1", qty: 2, note: none }, Item { sku: "b-2", note: "gift" }],
        status: Status.Open,
    }
    text := order.to_json()
    print(text)

    match Order.from_json(text) {
        back => print(back == order)
        ! e => print("{e.path}: {e.message}")
    }
}
```

```text
{"id":7,"items":[{"sku":"a-1","qty":2},{"sku":"b-2","qty":1,"note":"gift"}],"status":"open"}
true
```

The correspondence between types and JSON is fixed:

| Koo | JSON |
| --- | --- |
| `int`, `float` | a number |
| `bool` | `true` or `false` |
| `string` | a string |
| a list | an array |
| a map with string keys | an object |
| a structure | an object with a member for each field |
| an optional | the value, or nothing at all: a field that is `none` is left out |
| an enumeration without fields | the name of the variant, in snake case, as a string |
| an enumeration with fields | an object with the name of the variant under `"type"`, and its fields |

`from_json` can fail, with a `JsonError`, and it is exacting about what it accepts. The text must be JSON, and must fit the type: every field of a structure must be present, unless it is optional or has a default; a number must be a number, and a whole one where the field is an `int`. A member that the type has no field for is passed over, so that a program can read the part of a document that it cares about. When the text does not fit, the error says what was expected and what was found, and its `path` leads to the place:

```koo
type Item = { sku: string, qty: int = 1, note: string? }
type Order = { id: int, items: [Item] }

fn show(text: string) {
    match Order.from_json(text) {
        order => print(order)
        ! e => print("at `{e.path}`: {e.message}")
    }
}

fn main() {
    show(`{"id": 8, "items": [{"sku": "b-2"}], "extra": true}`)
    show(`{"id": 9, "items": [{"sku": "c-3", "qty": "two"}]}`)
    show(`{"id": 10, "items": [{"qty": 2}]}`)
    show(`{"items": []}`)
    show(`{"id": 11, "items": [`)
}
```

```text
Order { id: 8, items: [Item { sku: "b-2", qty: 1, note: none }] }
at `/items/0/qty`: expected a whole number, found a string
at `/items/0/sku`: `sku` is missing
at `/id`: `id` is missing
at `/items/0`: expected an object, found the end of the text
```

Raw strings, in backquotes, are convenient for JSON in a program, since JSON is full of double quotes and braces.

So a program that receives data from outside does not check it field by field. It declares the type that the data should have, reads it, and has either a value of that type, every field of which is what the type says, or an error that it can show to whoever sent the data. Chapter 10 puts this to work in a server.

The key of a field is its name. Data from elsewhere is not always named so: much of it says `accessToken` where a Koo program says `access_token`. An attribute after the type of a field gives the field another key, and an attribute on the line before a type names all its fields another way:

```koo
@json(rename: camel)
type Token = { access_token: string, expires_in: int = 3600, kind: string @json("token_type") }

fn main() ! JsonError {
    token := Token.from_json(`{"accessToken": "abc", "token_type": "bearer"}`)?
    print(token)
    print(token.to_json())
}
```

```text
Token { access_token: "abc", expires_in: 3600, kind: "bearer" }
{"accessToken":"abc","expiresIn":3600,"token_type":"bearer"}
```

The ways of naming are `camel`, `pascal` (`AccessToken`), `kebab` (`access-token`) and `snake`, which is the names as they are written and need not be said. A key that a field is given itself is used as it is, whatever the type says of the others; and two fields of one type cannot have the same key.

A type whose JSON is not the shape of its fields writes the two functions itself, with the signatures the compiler would have given them, and they are then used wherever a value of the type is written or read: alone, as a field of another structure, in a list.

```koo
type Money = { cents: int }

fn (self: Money) to_json() -> string {
    return "\"{self.cents / 100}.{self.cents % 100:02}\""
}

fn Money.from_json(text: string) -> Money ! JsonError {
    plain := text.trim().replace("\"", "")
    amount := float.parse(plain) else fail JsonError { message: "expected an amount, found {text}", path: "" }
    return Money { cents: (amount * 100.0).round() else 0 }
}

type Line = { sku: string, price: Money }

fn main() ! JsonError {
    line := Line { sku: "nails", price: Money { cents: 1999 } }
    print(line.to_json())
    print(Line.from_json(`{"sku": "glue", "price": "4.50"}`)?)
    match Line.from_json(`{"sku": "glue", "price": true}`) {
        other => print(other)
        ! e => print("at `{e.path}`: {e.message}")
    }
}
```

```text
{"sku":"nails","price":"19.99"}
Line { sku: "glue", price: Money { cents: 450 } }
at `/price`: expected an amount, found true
```

A type may write one of the two and leave the other to the compiler. Two things are to be known. A type with type parameters that writes its own is not yet used so inside other types, nor given the one it leaves out. And between the processes of a server a value goes to an actor and comes back field by field, whatever the type writes of itself for the world, so that it arrives as it was sent (Section 10.7); a handle of an actor is written as its name, and is not read back, since a handle is made by starting an actor and by nothing else.

The basic types and lists have `to_json` as well, and the value of a field may be any type that JSON can express, to any depth. What JSON cannot express cannot be written: a tuple, a function, a map whose keys are not strings.

## 8.8 Time

Programs that serve people deal in time: how long to wait for an answer, when an order was placed, whether a token has expired. Most languages give them numbers for the purpose, and leave it to the programmer to remember whether a given number is seconds or milliseconds, and since when. Koo has three types.

A `Duration` is a length of time. It is written as a number and a unit, and several of them may be run together, from the largest unit to the smallest:

    250ms     30s     5min     2h     1h30min     10us     7ns

The units are hours, minutes, seconds, and thousandths, millionths and thousand-millionths of a second. There is no unit for days, since a day by the calendar is not always the same length. Durations can be added and subtracted, multiplied and divided by an `int`, and compared, and that is all: a `Duration` is not a number, and cannot be added to one. The compiler will not let a timeout of `30` be passed where a `Duration` is wanted, which settles the question of the unit for good.

A `Time` is an instant, the same instant everywhere in the world. A duration can be added to a time or subtracted from it, giving a time, and one time can be subtracted from another, giving the duration between them. Two times cannot be added, which would mean nothing.

```koo
import std/time

timeout := 30s

fn main() {
    retry := 250ms
    print(retry * 4)
    print(timeout - 1500ms)
    print(1h30min / 3)
    print(timeout > retry)
    print("{timeout.seconds()} seconds, or {timeout.millis()} milliseconds")

    launch := Time.parse("1969-07-16T13:32:00Z") else Time.from_unix(0)
    landing := launch + 102h + 45min + 40s
    print(landing)
    print(landing - launch)
    print(landing > launch)

    started := time.uptime()
    time.sleep(20ms)

    print(time.now() > landing)
```

A duration is printed as it would be written in a program. A time is printed in the form of the standard called RFC 3339, in UTC, which is what the `Z` at the end says: the date, a `T`, and the time of day. `Time.parse` reads the same form, with `Z` or with an offset from UTC such as `+02:00`, and fails with a `ParseError` if the text is not a time. `Time.from_unix(n)` is the time `n` seconds after the beginning of 1970, which is how many systems count time, and `t.unix()` is its inverse. A `Duration` has the methods `seconds()`, which is a `float`, and `millis()`, `micros()` and `nanos()`, which are integers, for the places where a number is wanted after all.

The package `std/time` has four functions. `time.now()` is the time by the clock of the machine, and `time.today()`, which is for dates and comes below, the day it is. `time.sleep(length)` waits. And `time.uptime()` is how long the program has been running, by a clock that only goes forward: to find how long something took, take the difference of two of these, and not of two calls of `now`, since the clock of the machine can be set, forward or back, while a program runs.

Durations and times are JSON, as strings in the forms just described, so they can be fields of whatever a program reads and writes, and they can be sent to actors.

```koo
type Booking = { room: string, starts: Time, lasts: Duration }

fn main() {
    text := `{"room": "Lovelace", "starts": "2026-03-01T09:30:00+01:00", "lasts": "1h30min"}`
    match Booking.from_json(text) {
        booking => {
            print(booking)
            print("the room is free again at {booking.starts + booking.lasts}")
            print(booking.to_json())
        }
        ! e => print("{e.path}: {e.message}")
    }

    match Booking.from_json(`{"room": "Hopper", "starts": "tomorrow", "lasts": "1h"}`) {

        ! e => print("{e.path}: {e.message}")
    }
```

The third type is for what is not an instant at all. A birthday, the day an invoice falls due and the day a report covers are days of the calendar, and the same day wherever one is; to keep one as a `Time`, at some midnight, is to find it a day early or late as soon as it is read in another zone. A `Date` is a day, with no time of day and no zone, from the year 1 to the year 9999.

```koo
import std/time

type Invoice = { number: int, issued: Date, due: Date }

    print(invoice.to_json())

    print("{issued.midnight()} {(Time.parse("2026-01-31T23:30:00-02:00") else issued.midnight()).date()}")
    print(time.today() > issued)
```

A date is printed, and read by `Date.parse`, as the standard ISO 8601 writes one: the year, the month and the day, `2026-01-31`, and nothing more. `Date.of(year, month, day)` makes one, and fails with a `ParseError`, as `parse` does, for a day that no calendar has. A date has no arithmetic, since a day and a month are not the same length and `+ 1` would not say which was meant. `add_days` and `add_months` say it: a month after the 31st of January is the last day of February, which is what a person means by it. `a.days_until(b)` is the number of days from one date to the other. `d.midnight()` is the `Time` at which the day begins in UTC, and `t.date()` is the day of a time in UTC. `time.today()` is `time.now().date()`.

Dates are compared, and are JSON, as strings, and messages to actors, as times are; a date is a parameter of a query, and a column of the type `date` of a database (Sections 11.2 and 11.3).

Everything so far has been in UTC, and that is where a service should keep its times. But people live by the clocks of where they are, and a shop that closes at six in Paris closes at six by the clocks of Paris, which are an hour ahead of UTC in winter and two in summer, and change on a Sunday of March and of October. A `Zone` is a place's clocks, as the IANA time zone database records them: every change any government has made to them, and the rule they follow now.

```koo
import std/time

fn main() {
    paris := Zone.named("Europe/Paris") else Zone.utc()
    order := Time.parse("2026-07-01T16:30:00Z") else time.now()
    print("{paris.format(order)} {paris.offset(order)} {paris.abbreviation(order)}")
    (hour, minute, second) := paris.clock(order)
    print("{paris.date(order)} {hour}:{minute:02} open: {hour >= 9 and hour < 18}")
    // Six in the evening of a day in Paris, in winter and in summer.
    print("{paris.time(Date.of(2026, 1, 15) else paris.date(order), hour: 18) else order}")
    print("{paris.time(Date.of(2026, 7, 15) else paris.date(order), hour: 18) else order}")
    // The night the clocks go forward, half past two is never shown.
    print(paris.time(Date.of(2026, 3, 29) else paris.date(order), hour: 2, minute: 30) else order)
    print("{paris.parse("2026-12-24T20:00:00") else order} {Zone.named("Paris") else Zone.utc()}")
    print("{paris.to_json()} {Zone.named("Asia/Kathmandu") else paris} {(Zone.named("Asia/Kathmandu") else paris).format(order)}")
}
```

A zone is had by its name in the database, `Europe/Paris`, `America/New_York`, `Asia/Kolkata`, and `Zone.named` fails with a `ParseError` for a name the database does not have, `Paris` among them; `Zone.utc()` is UTC. The database is part of the program: it comes with the compiler, from a release that `Zone.release()` names, and a program says the same of a zone on every machine, a container with nothing else in it among them. `zone.offset(t)` is how far the zone's clocks are ahead of UTC at a time, and `zone.abbreviation(t)` what they are called then. `zone.date(t)` and `zone.clock(t)` are the day and the hour, minute and second that they show, and `zone.today()` is the day it is there now. `zone.format(t)` writes a time as RFC 3339 does with the zone's offset, which `Time.parse` reads back as the same instant.

The other way, from what the clocks show to the instant, is `zone.time(date, hour:, minute:, second:)`, and `zone.parse(text)` for a text without an offset. Twice a year it has something to decide. When the clocks are put back, an hour is shown twice, and the first of the two is meant. When they are put forward, an hour is never shown, and a time in it is taken as the clocks would have shown it had they not been changed, which they show as an hour later: so 02:30 on the 29th of March 2026 in Paris is 01:30 in UTC, which Paris calls 03:30. A program that must not be surprised by either keeps its times in UTC, and turns them into a zone's only to show them and to read what a person typed.

A zone is its name, so it is compared, a key and JSON as its name is, and it is a message to an actor. A setting of the environment may be one (Section 8.5), so that where a service is is told it, as the rest is: `TZ_OFFICE=Europe/Paris`.

## 8.9 Digests, Encodings and Chance

A program that talks to other programs over a network needs a few things that have nothing else in common: to prove that a message is from whom it says, to write bytes where only text may go, to keep a password without keeping it, and to make a number that nobody could have guessed. Four small packages provide them. All of them work on *lists of bytes*, `[byte]`, which is what `text.bytes()` returns for a string.

`std/hash` has `hash.sha256(data)`, the SHA-256 digest of some bytes: thirty-two bytes that are, for all that anyone can do, different for different data.

`std/encoding` writes bytes as text and reads them back. `encoding.hex` gives two hexadecimal digits for each byte, `encoding.base64` four letters for each three, and `encoding.base64_url` the same in the alphabet that is safe in an address, without the `=` at the end. Each has a reverse, `from_hex`, `from_base64` and `from_base64_url`, which fails with a `ParseError` on text that is not what it should be. `encoding.url(text)` and `encoding.from_url(text)` do for a string what must be done to put it in an address and get it out again.

`std/crypto` has `crypto.hmac_sha256(key, data)`, a digest that can be made only by someone who has the key. It is how one service proves to another that a message is its own: the sender puts the digest beside the message, and the receiver, who has the same key, makes the digest again and compares. The comparison is done with `crypto.equal(a, b)` and not with `==`, because `==` stops at the first byte that differs, and how long it took tells an attacker how many bytes he has right.

```koo
import std/crypto
import std/encoding
import std/hash

// Whether `signature`, as hexadecimal text, is that of `body` under `secret`.
fn signed(secret: string, body: string, signature: string) -> bool {
    claimed := encoding.from_hex(signature) else {
        return false
    }
    return crypto.equal(claimed, crypto.hmac_sha256(secret.bytes(), body.bytes()))
}

fn main() {
    body := `{"event": "paid", "order": 17}`
    secret := "whsec_not_a_real_one"

    signature := encoding.hex(crypto.hmac_sha256(secret.bytes(), body.bytes()))
    print(signature)
    print(signed(secret, body, signature))
    print(signed(secret, `{"event": "paid", "order": 18}`, signature))
    print(signed(secret, body, "not even hexadecimal"))

    print(encoding.hex(hash.sha256("abc".bytes())))
    print(encoding.base64("any bytes at all".bytes()))
    print(encoding.base64_url(hash.sha256("abc".bytes())))
    print(encoding.url("a name & a value/é"))
    print(encoding.from_url("a%20name%20%26%20a+value") else "?")
}
```

**Passwords.** A service must be able to check a password and should not be able to read one, so that whoever steals its database has stolen no passwords. `crypto.hash_password(password)` returns the text to keep in place of the password, and `crypto.verify_password(password, kept)` says whether a password is the one that was hashed. The text names its method, PBKDF2 with HMAC-SHA-256 and 600,000 rounds, and holds a salt that is different every time, so that two users with one password do not have one hash; the rounds are what make each guess of a thief expensive.

`std/random` is the package of chance. `random.int(low, high)` is a number from `low` up to, but not including, `high`, as a range is; `random.float()` is a number from zero up to one; `random.bytes(count)` is so many bytes; and `random.uuid()` is a name that nothing else has, in the customary form. A list has two methods of the same kind: `items.pick()` is one of its elements, or `none` if it has none, and `items.shuffle()` puts them in an order as likely as any other. All of these draw on the operating system's source of randomness, the one meant for keys, so a number from this package is fit to be a secret: there is no second, better, package to remember to use.

```koo
import std/crypto
import std/encoding
import std/random

fn main() {
    kept := crypto.hash_password("correct horse battery staple")
    print(kept.starts_with("pbkdf2-sha256$600000$"))
    print(crypto.verify_password("correct horse battery staple", kept))
    print(crypto.verify_password("correct horse battery stable", kept))

    var faces := [0, 0, 0, 0, 0, 0]
    for roll in 0..6000 {
        faces[random.int(1, 7) - 1] += 1
    }
    print(faces.all(count -> count > 800 and count < 1200))

    token := encoding.base64_url(random.bytes(24))
    print(token.len)
    id := random.uuid()
    print("{id.len} characters, and {id.split("-").len} groups")

    var deck := ["hearts", "spades", "clubs", "diamonds"]
    deck.shuffle()
    print(deck.sorted())
    print(deck.contains(deck.pick() else "none"))
}
```

## 8.10 A Log

A program that runs for months, with nobody watching, is known by what it writes down. The package `std/log` writes lines to the standard error output, each with the time, a *level* that says how much the line matters, and a message.

```koo
import std/log

type Order = { id: int, customer: string, total: float }

error Declined { reason: string }

fn charge(order: Order) ! Declined {
    if order.total > 100.0 {
        fail Declined { reason: "over the limit" }
    }
}

fn main() {
    log.info("the shop is open")
    for order in [Order { id: 17, customer: "ada", total: 19.5 }, Order { id: 18, customer: "bob", total: 250.0 }] {
        log.debug("charging {order.customer}")
        charge(order) else e => {
            log.error("order {order.id} of {order.customer} was not paid: {e.reason}")
            continue
        }
        log.info("order {order.id} paid, {order.total:.2}")
    }
    log.warn("the shop is closing")
}
```

```log
INFO  the shop is open
INFO  order 17 paid, 19.50
ERROR order 18 of bob was not paid: over the limit
WARN  the shop is closing
```

There are four functions, `log.debug`, `log.info`, `log.warn` and `log.error`, for the four levels, and the lines of `log.debug` did not appear: unless it is told otherwise a program writes the lines of level `info` and above. The lines above also lack their time, which was left out when the book was made because it would be different every time; a line as a program really writes it begins

    2026-03-01T09:30:00.250000Z INFO  the shop is open

with the time in UTC to the millionth of a second, always of that length, so that the lines of a log sort by their text.

Who decides what is logged, and how, is the person who runs the program, through its environment (Section 8.5), and not only the one who wrote it:

| | |
| --- | --- |
| `KOO_LOG_LEVEL` | the lowest level that is written: `debug`, `info`, `warn`, `error`, or `off` for nothing at all |
| `KOO_LOG` | `text`, for lines as above, or `json` |
| `KOO_LOG_TIME` | `off` leaves the time out, for a system that stamps every line itself |

The form `json` is for a program whose log is read by another program, and with it everything that reaches the standard error output is JSON, a line to an object: not only what the program logs but what is written on its behalf, such as a panic, or the line a server writes for each request (Section 10.7). And here is why the argument of `log.info` is written as it is. It looks like a string, and it is not one: like a query (Section 11.2), a string literal where a line of the log is expected is taken apart by the compiler, and the values in it are kept, each under the name of the expression that produced it. This is what the same program writes when `KOO_LOG` is `json`:

```json
{"level":"info","message":"the shop is open"}
{"level":"info","message":"order 17 paid, 19.50","order.id":17,"order.total":"19.50"}
{"level":"error","message":"order 18 of bob was not paid: over the limit","order.id":18,"order.customer":"bob","e.reason":"over the limit"}
{"level":"warn","message":"the shop is closing"}
```

Each line is one object. The message is there as a person would read it, and beside it are `order.id` and `order.customer`, as a number and a string, so that whoever searches the logs of a month for everything that happened to order 18 asks for the lines whose `order.id` is 18 and does not have to guess at the wording of messages. A value that is not a name or a field of one, such as `{a + b}`, is called `value1`, `value2` and so on, by its place in the line; a value with a format is kept as the text that the format made of it.

A line that is not wanted costs nothing. The values of a `log.debug` are not computed, and the line is not put together, unless lines of that level are being written, so a program can afford to say a great deal at the level `debug` and be run without it.

`log.set_level(log.Level.Debug)` sets the lowest level from inside the program, whatever the environment says; the levels are `Debug`, `Info`, `Warn`, `Error` and `Off`.
